# OptiFlow

OptiFlow is a portfolio-scale supply-chain allocation and disruption-analysis application. A Scala optimizer produces allocation reports for a demo warehouse/store network; a SvelteKit dashboard visualizes the results and compares independently optimized disruption scenarios. The goal is to make cost, fulfillment and shortage trade-offs inspectable rather than presenting an unexplained optimization score.

## What works in the repository

- **Allocation engine:** Scala 2.12 with Google OR-Tools; inspect the optimizer and its tests under `src/`. The optimizer is invoked through the CLI, not through a browser API.
- **Scenario Lab:** Generates a baseline and disruption reports, then compares total cost, transportation cost, shortage penalties, demand, fulfillment and shortage. The dashboard does **not** solve scenarios itself.
- **Dashboard:** SvelteKit/TypeScript reads JSON snapshots generated by the Scala CLI. It is a read-only local viewer.
- **Analytics:** A Python/DuckDB script exports scenario-impact analytics to CSV.
- **Orchestration:** An optional, manually triggered Airflow DAG generates snapshots, checks the dashboard contract and exports analytics. Airflow is not part of the default Docker Compose preview.
- **Automation:** GitHub Actions is configured to test Scala and the dashboard, generate real reports, validate analytics, and smoke-test the containerized UI. A configured check is not proof that a particular run passed.

## Prerequisites

For the direct local workflow: Java 17, sbt, Node.js 20 and npm. Docker with the Compose plugin is optional for the dashboard preview. Python 3 is used by analytics and integration checks; install DuckDB for the analytics command.

## Run locally

From the repository root, generate **both** report sets:

```sh
sbt test
sbt "runMain optiflow.AllocationReportCli datasets/demo output/allocation.json"
sbt "runMain optiflow.ScenarioSnapshotCli datasets/demo output/scenarios"
```

Then start the dashboard:

```sh
cd dashboard
npm install
npm run check
npm test
npm run dev
```

Open `http://127.0.0.1:5173` for the allocation overview and `http://127.0.0.1:5173/scenarios` for Scenario Lab. The app reads reports from the repository's `output/` directory; regenerate the snapshots and refresh the page to see updated results.

Alternatively, after generating the reports, run `docker compose up` from the repository root. See [Docker local preview](docs/docker-local.md) for mounts, startup behavior and cleanup. This Compose configuration previews the dashboard only; it does not run the optimizer.

## Validate generated analytics

```sh
python3 -m pip install 'duckdb>=1.1,<2'
python3 analytics/scenario_analytics.py output/scenarios output/scenario-impact.csv
python3 -m unittest discover -s analytics -p 'test_*.py' -v
python3 -m unittest discover -s airflow -p 'test_*.py' -v
```

The Airflow DAG is in `airflow/dags/optiflow_scenarios.py`. Running it requires a separate Airflow 2.8+ environment with Java, sbt, npm, Python and DuckDB on the worker, plus `OPTIFLOW_REPO_ROOT` pointing at the checkout. Python syntax/unit tests do **not** establish that the DAG ran in an Airflow scheduler.

## Data flow and boundaries

```text
datasets/demo
    |
    v
Scala allocation + scenario CLIs (OR-Tools)
    |
    +--> output/allocation.json ---------> SvelteKit allocation dashboard
    |
    +--> output/scenarios/*.json --------> SvelteKit Scenario Lab
                     |
                     +--> Python/DuckDB --> output/scenario-impact.csv
```

The scenario comparisons are based on generated reports, not fabricated frontend calculations. Costs and service levels are meaningful only for the input dataset, penalty assumptions and constraints used by each optimizer run. Treat the demo as an engineering demonstration, not a validated production planning system.

## Project status and scope

This repository is under active development. The local optimizer-to-report-to-dashboard path and CI checks must be executed successfully before calling the application end-to-end verified. Spark/Delta Lake and cloud deployment should be assessed against actual implemented code and tested separately; their presence in the intended architecture is **not** evidence of a running integration. No live service or production SLA is implied.

For reproducibility, use the checked-in demo dataset, run the Scala CLI to regenerate reports, and run the Scala/frontend/analytics test suites above. Do not commit generated credentials or cloud secrets.
